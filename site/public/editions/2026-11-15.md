## Tech & AI

### Italy fines Meta €805 million over Facebook gallery access

Italy’s data-protection authority announced an **€805 million fine** against Meta Platforms Ireland. The decision concerns a Facebook feature on Android that suggested gallery content for sharing. According to the authority, the feature had been available since 2023, was enabled by default and accessed photos, videos and associated metadata without specific, informed consent. The authority says roughly 20 million Italian Android users were affected.

Meta must, within 60 days, present a separate consent choice and keep the feature off unless the user opts in. It must report its actions within 30 days and implementation measures within 90 days. The fine is about 0.47% of Meta group global revenue, according to the authority.

The scope matters. This decision does **not** establish that Meta trained AI models on the accessed private media. The authority says a separate cloud-processing feature introduced in 2026 may be examined separately. Meta disputes the AI-training characterization. The confirmed issue here is consent and access to device media, not a finding about model training.

[Italian Garante decision and summary, November 14](https://garanteprivacy.it/home/docweb/-/docweb-display/docweb/10321080)

### Security catch-up — Lovable apps show how repeated access-control mistakes scale

*Original reporting: November 2. Updated research report accessed November 15; included because it was absent from the previous seven briefs.*

Crissy Field and Handelsblatt examined **159,041 Lovable projects** found in Common Crawl data from December 2025 through September 2026. Of those, 34,545 used Supabase. The researchers say 24,664 returned database records when the page first loaded; further read-only requests found email-bearing records in 10,560 tables across 7,403 sites.

The examples are serious: more than 80,000 profiles and 200,000 chat messages at one forum; over 1,000 identity-document records including passport numbers; customer, ticket, payment and property-management data; and large collections of contracts, invoices and messages. The researchers did not establish misuse.

The limitations are equally important. A record containing an email address may be public or test data; records without emails were missed; the Common Crawl sample is not representative of all Lovable applications; and the 30% figure applies only to the subset examined more closely. This is not evidence that 30% of all Lovable apps leak data. The practical lesson is narrower and stronger: generated code does not remove the need to test Supabase Row Level Security, unauthenticated API behavior and per-user data isolation before using real data.

### Security catch-up — ContextForge 1.1.1 fixes identity propagation that ignored per-server policy

*IBM bulletin: November 12; fixed release: November 10. Included because this specific issue was absent from the recent briefs.*

IBM says ContextForge MCP Gateway 1.0.0 through 1.1.0 could ignore the per-server switch intended to prevent upstream identity propagation. Tool calls and resource reads could therefore send user identity data—including user ID, email, groups or teams—to an upstream MCP server that was configured not to receive it. The same weakness involved replayable identity-propagation claims. IBM assigns CVSS 7.4 and fixes it in **1.1.1**.

If an immediate upgrade is impossible, IBM recommends disabling identity propagation globally with `IDENTITY_PROPAGATION_ENABLED=false` and restricting gateway access to trusted users. This is distinct from the earlier tool-name collision issue: it affects identity confidentiality and trust boundaries between a gateway and upstream servers.

## Open source & developer tools

### Recent popular — Chrome DevTools MCP 1.13.0 adds network mocks and logpoints

*Release: November 11. Current discovery signal: GitHub Trending daily at the November 15 cutoff. Included because the release was absent from the previous seven briefs.*

[ChromeDevTools/chrome-devtools-mcp](https://github.com/ChromeDevTools/chrome-devtools-mcp) gives coding agents an MCP server and CLI for driving and inspecting a live Chrome instance. Version **1.13.0** adds page-scoped network mocks, support for upstream mocked responses and DevTools logpoints. The release also fixes binary request-body preservation, cancellation serialization, cyclic `Error.cause` handling and several input-validation paths.

The practical use is not generic browsing; it is reproducible debugging. An agent can intercept one page’s API calls, observe console and network behavior, set a logpoint without changing source code and capture a performance trace. The boundary is broad: the server can inspect or modify anything in the connected browser. The project also enables its own usage statistics by default and may query CrUX for field performance data; both can be disabled. Use an isolated profile for sensitive work and pin a tested version rather than assuming `latest` is harmless.

[v1.13.0 release notes](https://github.com/ChromeDevTools/chrome-devtools-mcp/releases/tag/chrome-devtools-mcp-v1.13.0) · [README and privacy controls](https://github.com/ChromeDevTools/chrome-devtools-mcp)

### New release — agweb gives parallel macOS agents one visible browser

*v0.2.0 released November 14, inside this report window; surfaced through Show HN.*

[paul-nameless/agweb](https://github.com/paul-nameless/agweb) is a macOS WebKit browser controlled from the shell. Each agent gets a workspace and tabs, while a dashboard shows all activity without bringing windows to the foreground. Element references remain stable while the element exists, commands report page changes, named profiles can share logins and `ask` hands a tab to the user for MFA or CAPTCHA. Version **0.2.0** adds tracker blocking, improved waits, better text extraction and navigation reporting, and more selector and command controls.

This directly addresses a real multi-agent annoyance: automation windows stealing focus or headless runs becoming impossible to observe. But it requires macOS 26 or later, supports WebKit rather than Chrome DevTools Protocol, and shares a profile across agents if configured that way. That makes profile choice a security boundary; parallel convenience should not become accidental cross-task access.

### New project — DeepSeek V3 in 190 lines of pure JAX

*v1.0 released November 14, inside this report window; surfaced through Show HN.*

[Vaibhaav-Tiwari/deepseek-v3-jax](https://github.com/Vaibhaav-Tiwari/deepseek-v3-jax) reimplements the major DeepSeek V3 architectural ideas in 190 non-comment lines of pure JAX: Multi-head Latent Attention, decoupled RoPE, a shared-plus-routed expert mixture, auxiliary-loss-free expert balancing, a sequence-balance loss and multi-token prediction. The published demonstration is a **36.2 million-parameter** model trained from scratch on public-domain detective fiction—not DeepSeek’s 671-billion-parameter production model.

The project is unusually useful because it includes tests, fixed dependencies, exact data/checkpoint hashes, training logs and an ablation of expert balancing. The author reports about 2.6 hours of training on an M5 MacBook Air with 24 GB memory. Important limits remain: dense rather than sparse expert execution, no FP8 or DualPipe, 256-token context, and an untrusted Python pickle checkpoint can execute code when loaded.

### Catch-up worth researching — Google’s Elephant–Goldfish Model separates drafting from fresh review

*v0.1.1 released November 6; current discovery signal: GitHub Trending weekly at the cutoff. Included as a nine-day catch-up, not as a claim about historical rank.*

[google/elephant-goldfish-model](https://github.com/google/elephant-goldfish-model) is an open-source agent plugin for software design. The “elephant” keeps project context and drafts a specification; fresh “goldfish” reviewers see the document and referenced source material without the earlier conversation, making them less likely to inherit the drafter’s unstated assumptions. The human resolves trade-offs and approves the design. Other skills bootstrap codebase documentation and report drift between checked-in designs and implementation.

Version **0.1.1** packages current Claude and OpenAI runtimes, adds a TRIZ-style reviewer, improves review-context and severity preservation, and adds experimental Cursor, OpenCode and Copilot adapters. The project explicitly says fresh-subagent support is required for its review workflow and that its release ZIPs still lack exact native end-to-end validation. It is a good pattern to study for independent review, not evidence that multi-agent review automatically produces correct designs.

### Quick project note — Caveman 4.1.0 makes token-cutting claims easier to audit

*v4.1.0 released November 8; current discovery signal: GitHub Trending daily. Included as a seven-day project discovery, not because of cumulative stars.*

[JuliusBrussee/caveman](https://github.com/JuliusBrussee/caveman) is a skill and proxy that pushes coding agents toward controlled, short English and can compress large tool outputs. Its current README now compares against “answer concisely,” publishes cases where it loses and says its stronger mode cut output by 35% at the median in a ten-task Claude Opus 5.5 run. That is a small, project-authored benchmark, and a separate community issue reports results can disappear under another task mix.

Version **4.1.0** is mainly a safety and maintenance release: compression refuses files containing likely credentials, the recovery store can expire old handles instead of filling indefinitely, and dependencies and several agent integrations were repaired. It is worth testing only with a fixed task set and total input-plus-output cost; shorter prose is not automatically better, and compression itself can send file content to a model provider.

## Action suggestions

### Add a requirement-deviation gate before a coding agent edits

*Research submitted November 12; included as a catch-up because it was absent from the previous seven briefs.*

The SatisFix paper studies “specification satisficing”: an agent notices a requirement, then chooses a different implementation because it considers its own compromise acceptable. The authors tested five language models in two agent frameworks. They report that asking the agent to surface each planned deviation and its reason, then check those choices against the task, improved pass@1 by an average of 5.09 percentage points on DeepSWE and 7.06 points on the hard subset of SWE-bench Pro.

**A small workflow test:** use this gate only for bounded tasks with several explicit requirements. Before editing, have the agent list any choice that changes or weakens a requirement, quote the affected requirement and explain why. Then require a separate requirement-by-requirement check before code changes begin. These are author-reported benchmark results, not an independently reproduced guarantee; the extra pass also costs time and tokens.

[Original SatisFix paper](https://arxiv.org/abs/2611.16289)

### Checkpoint after proof and stop open-ended post-fix work

*Research submitted November 11; included as a catch-up because it was absent from the previous seven briefs.*

The Termination Lag paper retrospectively tested every distinct patch from runs covering five models, two agent frameworks and three SWE-bench datasets. The authors report that 38–82% of successful runs were already correct after the first source-code edit. Later steps made up a median 35–37% of successful Qwen3-Coder runs and 54–60% of Laguna-XS.2 runs in the core settings; 1–8% of runs later undid a correct patch.

**A practical guardrail, when the agent or version-control workflow can preserve a clean snapshot:** once the requested acceptance checks pass, keep that patch as a checkpoint. Allow further edits only when they address a named unmet requirement or failing check, and roll back if the same checks regress. The paper could identify the first correct patch only because hidden benchmark tests were run afterward; a real repository has no such oracle, so this supports evidence-based stopping and rollback, not “stop after the first edit.”

[Original Termination Lag paper](https://arxiv.org/abs/2611.14960)

## Business Opportunities

### Preflight security checks for AI-generated Supabase applications

**Verified demand signal:** the Lovable study found repeated unauthenticated access patterns across thousands of generated applications, while the platform audience includes users with limited security experience.

**Commercial hypothesis:** a small team could sell a narrowly scoped deployment gate that inventories Supabase tables, checks Row Level Security and anonymous-role permissions, runs synthetic cross-user reads, and produces a human-readable launch report. A hosted product could charge per project or per release; an open-source CLI could generate leads for paid review.

**Small validation:** build a read-only checker against intentionally vulnerable sample projects, then interview ten agencies or freelancers who ship Lovable/Supabase apps. Ask for the last access-control mistake they caught, what evidence a client requires before launch and whether a machine-generated report would change their workflow.

**Risks:** automated checks can miss business-logic flaws, scanning production data creates its own privacy obligations, and Lovable or Supabase could add comparable native checks. The product must not market a passing scan as a security guarantee.
